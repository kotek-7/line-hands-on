## 0. 設計の軸

第3回は「Realtimeを説明する講座」ではなく、次の課題連鎖として設計する。

> LINEを動かす
> → リロードすると消える
> → DBに残す
> → 2人で使うと相手に出ない
> → いまある知識だけで何とかする
> → Pollingなら動く
> → でも「スマートか？」
> → 変更されたときだけ受け取る
> → Realtimeで動く
> → 自分の投稿だけ二重になる
> → データの流れを整理して直す
> → 全員で使う

講義上はこれを「Challenge 1, 2, 3...」と明示しすぎず、スライドには自然に、

- 「まず、ここまで動かしてみよう」
- 「リロードしてみよう」
- 「2つのブラウザで使ってみよう」
- 「今ある知識だけで、なんとかしてみよう」
- 「あれ？」
- 「スマートか？」
- 「原因を探してみよう」

のような言葉を置く。challenge は講座のテーマではなく、講座を前へ進める暗黙の駆動方式とする。

今回の参加者は極基本程度のJavaScript知識を持つ前提なので、過去回より一段大きいステップで進める。

## 2. 講座設計の原則

### 原則A: 「説明単位」ではなく「攻略単位」で講座を刻む

1枚ごとに知識項目を消化するのではなく、

> いま何を動かしたいのか

を先に置く。

知識はその攻略に必要な分だけ、あとから差し込む。

### 原則B: challengeは「難問」である必要はない

小さなchallengeには、

- リロードしてみる
- 別ブラウザから送ってみる
- Consoleのpayloadを開いてみる
- 二重表示の原因を追う

も含まれる。

学習者自身の操作から、次の理解が生まれるようにする。

### 原則C: 正解だけでなく「一応動く解」を一度通る

大量コピーと同様に、Pollingも一度成立させる。

「悪いから使うな」と先に説明せず、

> 動く  
> でも違和感がある  
> もっと自然な仕組みが欲しい

という順序で進める。

### 原則D: 新技術の名前は必要性よりあと

Realtimeを冒頭で詳説しない。

「変更されたときだけ教えてほしい」という要求が生まれた後で、

> それをRealtimeでやる

と名前を与える。

### 原則E: 基礎知識がある今回は、1回の課題で複数の既知要素を組み合わせる

前案の、

> 1 messageを表示  
> → messages配列  
> → forEach  
> → submit

という刻み方は安全だが、今回の参加者には細かすぎる。

今回は最初から、

> 配列に入っているメッセージを全部表示し、フォームから新しいメッセージも追加する

までを一つの課題として渡す。

分からない人には「ヒント」を後出しする。

速い人には考える余地があり、極基本レベルの人にはヒントを足場として残せる。

# 9. Supabase実装上の現在の前提

2026-08-09時点のSupabase公式ドキュメントでは、DB変更購読にはBroadcastとPostgres Changesがあり、スケーラビリティ・セキュリティ面ではBroadcastが推奨され、Postgres Changesはより単純で設定が少ない方式として案内されている。

今回、Postgres Changesを選ぶ理由は本番アーキテクチャ上の推奨ではなく、教育上、

> 第2回のinsert
> → 第3回でそのINSERTを待ち受ける

という一本の因果を最短で見せられるため。

またPostgres Changesでは対象テーブルをsupabase_realtime publicationへ追加する設定が必要なので、これは講師側で事前設定する。

公式参照:

- Supabase: Subscribing to Database Changes  
  https://supabase.com/docs/guides/realtime/subscribing-to-database-changes
- Supabase: Postgres Changes  
  https://supabase.com/docs/guides/realtime/postgres-changes
- Supabase JavaScript: select  
  https://supabase.com/docs/reference/javascript/select
- Supabase JavaScript: insert  
  https://supabase.com/docs/reference/javascript/insert

# 10. 最終的な設計判断

この第3回では、Realtimeの説明そのものより、学習者が、

> 相手に出ない  
> → じゃあ取りに行けばいい  
> → 動いた  
> → でも、これは変だ  
> → 変更されたときだけ受け取れないか

という問題解決を自分の操作として通過することを重視する。そのあとにRealtimeを置けば、技術が「覚えるべきAPI」ではなく「自分がいま欲しかった仕組み」になる。

第1回の、

> 大量コピー → スマートか？ → JavaScript

第2回の、

> 長いDOM生成 → 長すぎる！ → uhtml

そして第3回の、

> 1秒ごとにselect → スマートか？ → Realtime

は、同じ講座設計思想でつながっている。

この反復を講師が説明する必要はない。参加者が講座の進み方として自然に経験すること自体を、暗黙の軸にする。
